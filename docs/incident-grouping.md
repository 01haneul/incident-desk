# 반복 이벤트의 사건 연결 설계

현재 상태: 설계 단계. 코드와 DB 변경 전이다.

## 1. 해결할 문제

하나의 장애가 지속되어 서로 다른 알림이 반복되면,
현재는 알림마다 새 장애 사건이 생성된다.

알림 각각은 이벤트로 보관하면서,
같은 장애 유형의 알림은 하나의 진행 중인 사건에 연결한다.

## 2. 요청 예시

```json
{
  "serviceKey": "payment-api",
  "incidentKey": "payment-approval-failure",
  "externalEventId": "evt-001",
  "title": "Payment approval failed"
}
```

- serviceKey: 장애가 발생한 서비스
- incidentKey: 같은 사건으로 묶을 장애 유형
- externalEventId: 개별 이벤트의 재전송 식별자

## 3. 연결 규칙

- incidentKey는 선택 입력이다.
- 생략하거나 null이면 기존처럼 새 사건을 생성한다.
  단, 동일 이벤트의 재전송이면 기존 접수 결과를 반환한다.
- 제공하면 1~100자의 영문 대소문자, 숫자, 점, 밑줄,
  콜론, 하이픈만 허용한다.
- 빈 문자열과 공백만 있는 값은 거절한다.
- 대소문자를 구분하며 입력값을 자동 변경하지 않는다.
- serviceKey와 incidentKey가 같고 상태가 OPEN인 사건을 찾는다.
- 해당 사건이 있으면 새 이벤트를 그 사건에 연결한다.
- 해당 사건이 없으면 새 OPEN 사건과 이벤트를 생성한다.
- 제목이 달라도 연결 기준이 같으면 같은 사건에 연결한다.
- 사건의 대표 제목과 생성 시각은 최초 접수 값을 유지한다.
- 각 이벤트에는 접수 당시의 제목과 incidentKey를 보관한다.

## 4. 재전송 처리와의 관계

- 재전송 식별 기준은 기존의 serviceKey와 externalEventId다.
- 같은 식별자에 제목과 incidentKey가 모두 같으면
  기존 접수 결과를 반환한다.
- 같은 식별자에 제목 또는 incidentKey가 다르면
  409 EVENT_ID_CONFLICT로 거절한다.
- externalEventId가 없으면 요청마다 새 이벤트를 저장한다.
  incidentKey가 있으면 해당 OPEN 사건에 연결할 수 있다.

## 5. 성공 응답

새 사건 생성 여부에 따라 HTTP 상태를 결정한다.

| 처리 | HTTP | eventCreated | incidentCreated |
| --- | --- | --- | --- |
| 새 사건과 새 이벤트 생성 | 201 | true | true |
| 기존 사건에 새 이벤트 연결 | 200 | true | false |
| 동일 이벤트 재전송 | 200 | false | false |

- 기존 응답의 eventId, incidentId, status, receivedAt은 유지한다.
- eventCreated와 incidentCreated를 응답에 추가한다.
- Location은 기존처럼 연결된 사건의 조회 주소를 사용한다.
- 200 응답의 처리 종류는 두 생성 여부 필드로 구분한다.

## 6. 저장과 동시 요청

- 사건 생성과 이벤트 저장은 하나의 트랜잭션으로 처리한다.
- 새 사건을 만든 뒤 이벤트 저장에 실패하면 사건도 롤백한다.
- 기존 사건에 이벤트를 추가하다 실패하면 기존 사건은 유지하고
  실패한 이벤트는 저장하지 않는다.
- 같은 서비스와 incidentKey에 OPEN 사건은 최대 하나만 허용한다.
- 이 규칙은 애플리케이션 조회와 DB 제약조건으로 보장한다.
- 동시 생성 충돌 후에는 실패한 트랜잭션을 롤백하고
  새 트랜잭션에서 기존 사건 연결을 재시도한다.
- 동일 이벤트 재전송의 중복 방지 제약조건도 유지한다.

## 7. 검증 기준

- 같은 연결 기준의 서로 다른 이벤트 두 건:
  사건 1건, 이벤트 2건.
- 서로 다른 incidentKey:
  별개의 사건 생성.
- 서로 다른 serviceKey:
  별개의 사건 생성.
- incidentKey 생략:
  기존 요청 동작 유지.
- 같은 이벤트 번호에 incidentKey만 변경:
  409, 추가 저장 없음.
- 같은 연결 기준의 서로 다른 이벤트 두 건을 동시 접수:
  OPEN 사건 1건, 이벤트 2건.
- 이벤트 저장 실패:
  불필요한 새 사건이 남지 않음.
- 인증 및 기존 재전송 테스트도 계속 통과.

## 8. 선택 이유와 한계

서비스만으로 묶으면 서로 다른 장애가 합쳐질 수 있다.
제목으로 묶으면 문구 변화에 따라 같은 장애가 나뉠 수 있다.

감시 시스템이 명시한 incidentKey를 사용해 연결 기준을 고정한다.
따라서 감시 시스템의 키 부여 규칙이 정확해야 한다.

현재 연결 대상은 OPEN 사건이다.
사건 확인·해결과 이후 재발 처리의 검증은 상태 관리 구현에서 진행한다.
