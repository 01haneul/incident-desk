# 첫 데이터 모델

## 1. 설계 범위

- 첫 장애 이벤트 접수와 장애 사건 상세 조회를 지원한다.
- 단일 조직을 기준으로 한다.
- 현재 단계에서는 유효한 접수 요청마다 새 사건을 생성한다.
- 반복 이벤트 연결과 중복 요청 처리는 후속 구현이다.

## 2. incidents: 장애 사건

| 컬럼 | 논리 타입 | 필수 | 설명 |
|---|---|---|---|
| id | 64비트 정수 | O | 서버가 생성하는 기본키 |
| service_key | 문자열(100) | O | 장애가 발생한 서비스 식별자 |
| title | 문자열(200) | O | 사건의 대표 제목 |
| status | 문자열(20) | O | 첫 구현에서는 OPEN |
| created_at | 시각 | O | 서버에서 기록한 사건 생성 시각 |

## 3. events: 접수한 이벤트

| 컬럼 | 논리 타입 | 필수 | 설명 |
|---|---|---|---|
| id | 64비트 정수 | O | 서버가 생성하는 기본키 |
| incident_id | 64비트 정수 | O | 연결된 장애 사건의 외래키 |
| service_key | 문자열(100) | O | 접수 당시의 서비스 식별자 |
| title | 문자열(200) | O | 접수 당시의 장애 제목 |
| received_at | 시각 | O | 서버에서 기록한 접수 시각 |

## 4. 관계와 제약조건

- 하나의 장애 사건에 여러 이벤트가 연결될 수 있다.
- 각 이벤트는 반드시 하나의 장애 사건에 연결된다.
- events.incident_id는 incidents.id를 참조한다.
- 사건과 이벤트의 기본키는 각각 독립적으로 생성한다.
- 같은 service_key를 가진 사건이 여러 개 존재할 수 있다.
- 첫 구현에는 사건과 이벤트의 삭제 기능을 제공하지 않는다.
- 외래키는 사건 삭제 시 이벤트를 자동 삭제하지 않도록 설정한다.

## 5. 값과 시각의 규칙

- 문자열 길이와 입력 규칙은 API 계약을 따른다.
- 모든 필수 컬럼에 NOT NULL 제약조건을 적용한다.
- 초기 사건 상태는 서버에서 OPEN으로 지정한다.
- 시각은 UTC 기준으로 저장하고 API에서는 Z가 붙은 형식으로 응답한다.
- DB 제품에 맞는 실제 컬럼 타입은 개발 환경 선택 시 확정한다.

## 6. 저장 순서와 트랜잭션

1. 요청 데이터를 검증한다.
2. 접수 시각을 생성한다.
3. 새 장애 사건을 저장하고 사건 식별자를 얻는다.
4. 해당 사건 식별자를 가진 이벤트를 저장한다.
5. 두 저장을 하나의 트랜잭션으로 커밋한다.
6. 커밋에 성공한 후 API 성공 응답을 보낸다.

저장 중 실패하면 두 데이터 모두 롤백한다.
첫 접수에서는 사건 생성 시각과 이벤트 접수 시각에 같은 값을 사용한다.

## 7. 첫 조회와 인덱스

- 상세 조회는 incidents의 기본키로 조회한다.
- 사건별 이벤트 조회를 위해 events.incident_id에 인덱스를 둔다.
- 다른 인덱스는 실제 조회 조건과 실행 계획을 보고 추가한다.

## 8. 후속 설계 과제

- 외부 이벤트의 식별 기준과 중복 방지 제약조건
- 반복 이벤트를 같은 사건으로 묶는 기준
- 담당자와 대응 이력
- 자동 전환 및 알림 재시도 작업
