# 요구사항 

## 1. 사용자와 문제

- 외부 감시 시스템은 서비스에서 발생한 장애 이벤트를
  전송한다.
- 운영 담당자는 접수된 장애 사건을 조회하고 대응한다.
- 반복 알림과 미확인 장애를 추적할 수 있어야 한다.

## 2.  용어

- 이벤트 : 외부 시스템이 전송한 장애 정보 한 건
- 장애 사건 : 담당자가 확인하고 해결하는 관리 단위
- 서비스 : 장애가 발생한 시스템. 예 : payment-api

## 3. 첫 구현 범위 

단일 조직의 로컬 개발 환경을 기준으로 한다.

1. 장애 이벤트 한 건을 HTTP 요청으로 받는다.
2. 필수 입력값을 검증한다.
3. 이벤트와 새 장애 사건을 하나의 트랜잭션으로 저장한다.
4. 생성된 장애 사건의 식별자를 응답한다.
5. 식별자로 장애 사건을 조회한다

## 4. 첫 구현 규칙

- 서비스 식별자와 장애 제목은 필수다
- 장애 제목은 공백만으로 구성될 수 없다.
- 새 장애 사건의 초기 상태는 OPEN이다.
- 접수 시각은 서버에서 기록한다.
- 입력값이 잘못되면 이벤트와 장애 사건 모두 저장하지 않는다.
- 저장 도중 실패하면 이벤트와 장애 사건 모두 저장하지
  않는다.
- 존재하지 않는 장애 사건을 조회하면 404를 반환한다.

# 후속 구현 

- 외부 시스템 인증
- 동일 이벤트 재전송의 중복 처리
- 반복 이벤트를 진행 중인 장애 사건에 연결
- 담당자 배정과 확인 · 해결
- 미확인 장애의 담당자 전환
- 알림 전송과 실패 재시도
- 대응 이력 조회

인증을 구현하기 전까지 로컬 환경에서만 실행된다.


## 다음 구현: 동일 이벤트 재전송의 중복 처리

### 해결할 문제

감시 시스템이 응답을 받지 못해 같은 이벤트를 재전송하면,
동일한 장애 사건과 이벤트가 중복 생성될 수 있다.

### 처리 규칙

- 외부 이벤트 번호 externalEventId를 요청에 추가한다.
- 중복 식별 기준은 serviceKey와 externalEventId의 조합이다.
- 같은 식별자와 같은 내용의 재전송에는 기존 접수 결과를 반환한다.
- 재전송으로 사건과 이벤트를 추가 생성하지 않는다.
- 같은 식별자에 다른 제목이 전달되면 409 Conflict로 거절한다.
- 서로 다른 externalEventId는 별개의 이벤트로 처리한다.
- 동시에 같은 이벤트를 보내도 중복 생성되지 않아야 한다.
- 실패한 접수로 사건만 남지 않아야 한다.

### 기존 요청과의 호환

- 첫 단계에서는 externalEventId를 선택 입력으로 추가한다.
- 번호를 생략한 기존 요청은 지금처럼 매번 새로 접수한다.
- 재전송 중복 방지는 externalEventId를 제공한 요청에 적용한다.

### 이번 범위의 경계

서로 다른 이벤트를 하나의 진행 중인 사건에 묶는 기능은
별도의 후속 작업으로 구현한다.
