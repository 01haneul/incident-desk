# Incident Desk 요구사항

Incident Desk는 외부 감시 시스템이 보낸 장애 이벤트를 접수하고, 운영 담당자가 사건을 배정·확인·해결하는 과정을 기록하는 백엔드 서비스다. 단일 조직의 로컬 환경을 기준으로 최초 기획 범위의 구현과 검증을 완료했다.

## 1. 사용자와 문제

- 외부 감시 시스템은 장애 이벤트를 전송한다. 응답을 받지 못하면 같은 이벤트를 다시 보낼 수 있다.
- 운영 담당자는 여러 알림이 같은 장애에 관한 것인지 파악해야 한다. 사건의 현재 상태와 담당자, 이전 대응 내역을 조회할 수 있어야 한다.
- 담당자에게 알림을 보내는 과정에서 일시적인 오류가 발생하면 전송을 재시도해야 한다.

## 2. 용어와 식별 기준

| 용어 | 의미 |
|---|---|
| 이벤트 | 외부 감시 시스템에서 접수한 개별 장애 알림 한 건 |
| 사건 | 담당자를 배정하고 상태를 변경하는 장애 대응 단위. 한 사건에 여러 이벤트가 연결될 수 있다. |
| `serviceKey` | 장애가 발생한 서비스를 식별하는 값. 예를 들어 `payment-api`가 있다. |
| `externalEventId` | 같은 서비스에서 이미 접수한 이벤트의 재전송을 식별하는 선택값 |
| `incidentKey` | 같은 서비스에서 서로 다른 이벤트를 하나의 열린 사건에 연결하는 선택값 |

## 3. 이벤트 접수와 사건 조회

1. `POST /api/events`로 장애 이벤트를 접수한다. 서비스 식별자와 제목은 필수이며, 공백으로만 구성된 제목은 거절한다.
2. 접수 시각은 서버가 기록한다. 새 사건의 초기 상태는 `OPEN`이다.
3. 새 사건과 첫 이벤트는 하나의 트랜잭션에서 저장한다. 입력 검증이나 저장이 실패하면 사건 또는 이벤트만 남지 않아야 한다.
4. 응답에 이벤트 ID와 사건 ID를 포함한다. `eventCreated`와 `incidentCreated`로 각각 새로 생성됐는지 표시한다.
5. `GET /api/incidents/{incidentId}`로 사건을 조회한다. 존재하지 않는 사건은 `404`를 반환한다.

## 4. 이벤트 재전송과 반복 장애 연결

재전송은 **같은 알림이 다시 도착한 경우**다. 반복 장애는 **별개의 알림들이 같은 장애를 가리키는 경우**다. 서버는 먼저 재전송 여부를 판별하고, 새 이벤트라면 연결할 사건을 찾는다.

| 접수 조건 | 처리 결과 |
|---|---|
| `serviceKey`와 `externalEventId`가 같고 제목과 `incidentKey`도 같다. | 기존 접수 결과를 `200`으로 반환한다. 사건과 이벤트 수는 그대로 유지한다. |
| `serviceKey`와 `externalEventId`가 같지만 제목 또는 `incidentKey`가 다르다. | `409 EVENT_ID_CONFLICT`를 반환한다. 기존 데이터를 보존한다. |
| 새 이벤트의 `serviceKey`와 `incidentKey`가 같은 `OPEN` 사건이 있다. | 해당 사건에 새 이벤트만 추가하고 `200`을 반환한다. 사건의 최초 제목과 생성 시각을 유지한다. |
| 새 이벤트에 `incidentKey`가 없거나 연결할 `OPEN` 사건이 없다. | 새 사건과 이벤트를 생성하고 `201`을 반환한다. |

`externalEventId`를 생략하면 요청마다 새 이벤트를 접수한다. 이 경우에도 `incidentKey`가 있으면 기존 `OPEN` 사건에 연결할 수 있다. 같은 외부 이벤트가 동시에 도착해도 한 번만 저장돼야 한다.

상세 규칙은 [재전송 처리 설계](idempotency.md)와 [사건 연결 설계](incident-grouping.md)에 기록했다.

## 5. 담당자 배정과 상태 변경

| 작업 | 허용 조건과 결과 |
|---|---|
| 최초 배정 | 담당자가 없는 `OPEN` 사건에 담당자를 배정한다. |
| 담당자 인계 | `OPEN` 사건에서 요청의 현재 담당자가 저장된 담당자와 일치하면 새 담당자로 변경한다. |
| 사건 확인 | `OPEN` 사건을 `ACKNOWLEDGED`로 변경한다. |
| 사건 해결 | `ACKNOWLEDGED` 사건을 `RESOLVED`로 변경한다. |

이미 확인한 사건에 확인 요청을 다시 보내면 성공으로 응답하고 이력은 한 건으로 유지한다. 인계 요청의 현재 담당자가 일치하지 않거나 이미 확인된 사건을 인계하려 하면 `409 INCIDENT_STATUS_CONFLICT`를 반환한다. 거절된 요청은 상태, 담당자, 이력을 변경하지 않는다.

## 6. 담당자 알림과 대응 이력

- 담당자 배정·인계 시 새 담당자에게 보낼 알림을 기록한다.
- 알림 전송이 실패하면 재시도한다. 같은 알림의 재시도에는 동일한 `Idempotency-Key`를 사용하고, 전송 상태와 시도 횟수를 저장한다.
- 배정·인계·확인·해결로 실제 변경이 발생하면 사건 이력을 기록한다. 담당자 변경 이력에는 이전 담당자와 새 담당자를 남긴다.
- `GET /api/incidents/{incidentId}/history`로 사건 이력을 조회한다. `afterId`를 지정하면 해당 이력 ID보다 큰 항목을 ID 오름차순으로 반환한다.

## 7. 인증과 실행 범위

- 이벤트 접수 요청은 `X-API-Key` 헤더로 인증한다. 인증에 실패하면 접수 서비스를 호출하지 않는다.
- 서버에 API 키가 설정되지 않았거나 공백이면 HTTP 서버 시작을 차단한다.
- DB 비밀번호와 API 키는 환경 변수로 관리한다.
- 운영자 인증, 서비스별 권한 분리, 외부 배포는 후속 범위로 남긴다.

## 8. 완료 판정

로컬 서버의 실제 HTTP 응답과 MySQL 저장 결과를 대조해 이벤트 접수·조회, 재전송 처리, 반복 장애 연결, 담당자 배정·인계, 상태 변경, 알림 재시도, 이력 조회를 검증했다.

별도의 빈 MySQL 인스턴스에서도 초기화 SQL `001`~`007`을 적용했다. 새 복제본에서 이벤트 접수 `201`, 사건 상세 조회 `200`, 응답 ID와 일치하는 DB 행을 확인했다. 테스트 DB 포트를 해당 인스턴스로 지정한 뒤 전체 Gradle 테스트도 통과했다.

실행 절차는 [README](../README.md), 요청·응답 형식은 [API 계약](api.md), 관찰 결과는 [검증 기록](verification.md)에서 확인할 수 있다.
