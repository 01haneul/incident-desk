# 보안 설계

## 1. 외부 시스템 인증

현재 상태: 구현 및 로컬 검증 완료.

### 해결할 문제

인증 없이 장애 이벤트를 접수하면 허용하지 않은 요청으로
잘못된 장애 사건과 이벤트가 저장될 수 있다.

이벤트를 전송하는 감시 시스템의 API 키를 확인한 뒤 접수한다.

### 인증 방식

- 단일 조직의 감시 시스템 한 개를 기준으로 한다.
- 감시 시스템과 Incident Desk가 하나의 API 키를 공유한다.
- POST /api/events 요청의 X-API-Key 헤더로 전달한다.
- 매 요청마다 키를 확인한다.
- API 키는 MySQL 비밀번호와 별도로 생성한다.
- 서버의 실제 키는 INGESTION_API_KEY 환경 변수로 관리한다.
- 키가 없거나 공백이면 서버 시작을 실패시킨다.
- 소스 코드, Git, 로그, 오류 응답에 실제 키를 남기지 않는다.
- URL이나 요청 JSON에 API 키를 넣지 않는다.

요청 형식:

POST /api/events
Content-Type: application/json
X-API-Key: <환경 변수로 관리하는 실제 키>

### 처리 순서

1. API 키를 확인한다.
2. 인증에 성공하면 요청 JSON과 입력값을 검증한다.
3. 기존 중복 처리 규칙에 따라 이벤트를 접수한다.
4. 처리 결과를 응답한다.

인증에 실패하면 접수 서비스를 호출하지 않고,
장애 사건과 이벤트를 저장하지 않는다.

### 인증 실패 응답

키가 없거나 잘못되면 모두 같은 응답을 반환한다.

상태 코드: 401 Unauthorized
WWW-Authenticate: ApiKey realm="incident-desk"

{
  "code": "UNAUTHORIZED",
  "message": "인증 정보가 없거나 올바르지 않습니다.",
  "fieldErrors": []
}

응답에 전달받은 키나 서버의 실제 키를 포함하지 않는다.

### 인증 성공 이후의 처리

| 조건 | 기대 결과 |
| --- | --- |
| 정상적인 최초 접수 | 201, 사건과 이벤트 생성 |
| 동일 이벤트 재전송 | 200, 추가 생성 없음 |
| 같은 이벤트 번호에 다른 제목 | 409, 추가 생성 없음 |
| 잘못된 입력값 | 400, 저장 없음 |

## 2. 적용 범위와 한계

- 이번 인증의 적용 대상은 POST /api/events다.
- 사건 조회 API의 운영자 인증은 후속 작업이다.
- 현재는 로컬 개발 환경에서 검증한다.
- 로컬 실행 주소는 127.0.0.1로 제한한다.
- 외부 통신 환경에서는 HTTPS를 적용해야 한다.
- 공유 키를 가진 감시 시스템은 모든 serviceKey로 접수할 수 있다.
- 감시 시스템별 키 발급과 서비스별 권한은 후속 작업이다.
- 키 교체는 환경 변수 변경과 서버 재시작으로 처리한다.

## 3. 검증 기준

- 키가 없으면 401이고 접수 서비스를 호출하지 않는다.
- 잘못된 키도 동일한 401 응답을 반환한다.
- 올바른 키가 있어야 입력 검증과 접수를 진행한다.
- 인증 실패 요청 전후에 DB 데이터 수가 변하지 않는다.
- 인증 성공 이후에도 기존 중복 처리 규칙이 유지된다.
- 기존 테스트와 새 인증 테스트가 모두 통과해야 한다.
